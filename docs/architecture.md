# Clash of Clans Analytics Bot

## Общее описание

Clash of Clans Analytics Bot — это автономное серверное приложение на C++, предназначенное для автоматического сбора,
хранения, анализа и уведомления о событиях в кланах Clash of Clans.

Приложение регулярно получает данные через официальный Clash of Clans API, сохраняет их в локальную SQLite базу данных,
хранит историческую информацию о клане и игроках, формирует аналитические отчеты и отправляет их в Telegram.

Основная задача системы — предоставить руководству клана инструменты для контроля активности игроков, отслеживания
изменений состава, анализа войн, лиги клановых войн и рейдовых выходных.

---

Система предназначена для:

* глав кланов;
* со-лидеров;
* ответственных за управление составом клана;
* аналитиков клановой статистики.

# Основной функционал

## Мониторинг клана

Система сохраняет полную историю состояния клана:

* количество участников;
* уровень клана;
* трофеи;
* очки столицы;
* параметры набора игроков;
* военную статистику;
* характеристики лиги.

Для этого используются периодические снимки состояния клана (ClanSnapshot).

---

## Мониторинг игроков

Система отслеживает:

* вступления игроков;
* выходы игроков;
* изменения роли;
* изменения уровня ратуши;
* изменения количества трофеев;
* пожертвования;
* место игрока в клане.

Для этого используются:

* Player;
* PlayerSnapshot;
* ClanMembership.

---

## История состава клана

Каждое вступление и выход игрока сохраняется в отдельную таблицу истории.

Это позволяет:

* определять новичков;
* находить ушедших игроков;
* анализировать продолжительность пребывания игроков в клане;
* строить исторические отчеты по составу.

---

## Клановые войны

Система собирает информацию о:

* регулярных войнах;
* дружественных войнах;
* войнах лиги клановых войн.

Для каждой войны сохраняются:

* информация о войне;
* информация о противнике;
* составы участников;
* все атаки;
* результаты войны.

Поддерживаются сущности:

* Clanwar;
* ClanwarClan;
* ClanwarMember;
* ClanwarAttack.

---

## Лига клановых войн (CWL)

Система сохраняет:

* сезоны CWL;
* зарегистрированных участников;
* все войны сезона;
* статистику участников.

Используются сущности:

* ClanwarsLeagueSeason;
* ClanwarsLeagueMember;
* CompleteClanwarsLeagueData.

---

## Рейд-выходные

Система сохраняет:

* информацию о рейде;
* количество проведенных атак;
* заработанную добычу;
* разрушенные районы;
* индивидуальную активность игроков.

Используются сущности:

* ClanRaid;
* PlayerRaidSnapshot.

---

## Система отчетов

На основе собранных данных формируются автоматические отчеты.

Примеры:

* игроки, покинувшие клан;
* новые участники;
* игроки, не использовавшие атаки на войне;
* игроки, не выполнившие рейдовые атаки;
* нарушения зеркальной системы атак;
* результаты завершенных войн;
* результаты CWL.

---

## Система уведомлений

Все уведомления отправляются в Telegram.

Система гарантирует, что одно и то же событие не будет отправлено повторно.

Для этого используется таблица notifications, в которой фиксируются уже обработанные события.

## API Layer

Центральной точкой взаимодействия с внешним API является класс APIClient.

Его задачи:

* выполнение HTTP-запросов;
* обработка ошибок сети;
* получение JSON-ответов;
* предоставление данных сервисам.

Технологии:

* CPR
* nlohmann/json

---

## Service Layer

Все сервисы наследуются от интерфейса IService.

Сервисы отвечают за:

* получение данных через APIClient;
* преобразование JSON в доменные модели;
* сохранение данных;
* возврат результатов синхронизации.

Каждый сервис изолирован и отвечает за собственную область данных:

* клан;
* войны;
* CWL;
* рейды.

---

## Repository Layer

Доступ к базе данных реализован через репозитории.

Основные репозитории:

* ClanRepository
* ClanwarRepository
* ClanwarsLeagueRepository
* RaidRepository

Репозитории инкапсулируют SQL-запросы и полностью скрывают работу с SQLite от сервисов.

---

## Database Layer

В качестве СУБД используется SQLite.

База данных содержит таблицы для:

* кланов;
* игроков;
* истории членства;
* снимков кланов;
* снимков игроков;
* войн;

* атак;
* сезонов CWL;
* участников CWL;
* рейдов;
* участников рейдов;

---

## Transaction Management

Все операции записи выполняются внутри транзакций.

Для управления транзакциями используется отдельный RAII-класс TransactionGuard.

Он гарантирует:

* атомарность операций;
* автоматический rollback при ошибках;
* автоматический commit при успешном завершении.

---

## Migration System

Для управления щемой базы данных используется MigrationManager.

Он отвечает за:

* создание структуры БД;
* применение миграций;
* хранение версии схемы;
* обновление структуры базы данных между версиями приложения.

## Multi-Clan Architecture

Система поддерживает одновременное обслуживание нескольких кланов и независимую отправку уведомлений в несколько Telegram-чатов.

Список отслеживаемых кланов хранится в базе данных и больше не зависит от конфигурационного файла приложения.

Для связи кланов и Telegram-чатов используется система подписок.

Основные таблицы:

* `clans`
* `telegram_chats`
* `clan_subscriptions`

Связь между кланами и чатами реализована по принципу «многие ко многим»:

* один клан может иметь несколько подписчиков;
* один Telegram-чат может быть подписан на несколько кланов.

Во время каждого цикла синхронизации `ClanManager` получает список активных кланов из базы данных и последовательно запускает синхронизацию каждого из них.

После генерации Domain Events `NotificationService` определяет список Telegram-чатов, подписанных на соответствующий клан, и независимо отправляет уведомление каждому подписчику.

Благодаря такой архитектуре сервисы синхронизации не содержат информации о Telegram, а транспортный слой не зависит от количества обслуживаемых кланов.

На текущем этапе управление списком кланов и подписок выполняется вручную через базу данных. Архитектура уже подготовлена для дальнейшей реализации управления подписками непосредственно через Telegram.

# Event Layer

Для разделения логики синхронизации данных и обработки бизнес-событий в проекте реализована внутренняя событийная система (In-Memory Event System).

После завершения синхронизации сервисы формируют список доменных событий (Domain Events), которые описывают произошедшие изменения, но не содержат логики уведомлений.

Примеры событий:

* PlayerJoinedClanEvent
* PlayerLeftClanEvent
* PlayerRoleChangedEvent
* WarEndedEvent
* RaidEndedEvent

Все события являются простыми структурами данных и объединены в тип `std::variant`, что обеспечивает строгую типизацию без использования наследования и RTTI.

Каждый сервис отвечает только за обнаружение изменений и генерацию соответствующих Domain Events.

После завершения полного цикла синхронизации всех сервисов события передаются в `EventDispatcher`, который последовательно передает их зарегистрированным обработчикам.

На текущем этапе единственным обработчиком событий является `NotificationService`, однако архитектура позволяет в дальнейшем подключать дополнительные обработчики (логирование, веб-интерфейс, Discord, статистику и другие) без изменения сервисов синхронизации.

---

# Reporting Layer

Слой отчетов отвечает исключительно за преобразование Domain Events в человекочитаемые сообщения.

Базовый интерфейс:

* `IReportFormatter`

Каждый форматтер отвечает только за:

* получение конкретного Domain Event;
* получение необходимых данных из репозиториев;
* формирование текста уведомления.

Форматтеры не содержат бизнес-логики обнаружения событий и не выполняют отправку сообщений.

Каждый тип события имеет собственный форматтер, например:

* PlayerJoinedClanFormatter
* PlayerLeftClanFormatter
* PlayerRoleChangedFormatter
* WarEndedFormatter
* RaidEndedFormatter

Такое разделение позволяет независимо расширять список событий и отчетов без изменения существующей архитектуры.

---

# Notification Layer

Система уведомлений полностью отделена от сервисов синхронизации.

Основные компоненты:

* `EventDispatcher`
* `NotificationService`
* `TelegramNotifier`

Ответственность компонентов:

**EventDispatcher**

* получает Domain Events после завершения цикла синхронизации;
* последовательно передает события зарегистрированным обработчикам.

**NotificationService**

* принимает Domain Event;
* определяет соответствующий `ReportFormatter`;
* получает список Telegram-чатов, подписанных на клан;
* формирует текст сообщения;
* инициирует отправку через `TelegramNotifier`.

**TelegramNotifier**

Отвечает исключительно за доставку сообщений через Telegram Bot API и не содержит логики формирования отчетов или определения получателей.

Такое разделение обеспечивает слабую связанность между синхронизацией данных, формированием отчетов и транспортным уровнем доставки уведомлений.

# Основной цикл работы

Центральным координатором системы является `ClanManager`.

Каждые 30 минут запускается цикл синхронизации.

Последовательность работы:

1. `ClanManager` получает список отслеживаемых кланов.
2. Для каждого клана запускаются сервисы синхронизации.
3. Сервисы получают данные через `APIClient`.
4. Данные преобразуются в доменные модели.
5. Репозитории сохраняют изменения в SQLite.
6. Сервисы обнаруживают изменения и формируют Domain Events.
7. Domain Events возвращаются в составе `SyncResult`.
8. После завершения синхронизации всех сервисов `ClanManager` передает накопленные события в `EventDispatcher`.
9. `EventDispatcher` передает события `NotificationService`.
10. `NotificationService` формирует отчеты с помощью соответствующих `ReportFormatter`.
11. `TelegramNotifier` отправляет готовые сообщения во все Telegram-чаты, подписанные на соответствующий клан.

# Архитектурные принципы

Проект использует следующие подходы:

* **Repository Pattern**
* **Service Layer Pattern**
* **RAII**
* **Interface-Based Design**
* **Separation of Concerns**
* **Transactional Persistence**
* **Idempotent Notifications**
* **Domain-Oriented Design**
* **Partial Event-Driven Architecture** — означает, что сервисы публикуют доменные события вместо прямого взаимодействия со слоем уведомлений. Обработка событий выполняется отдельным слоем (`EventDispatcher` и `NotificationService`), что снижает связанность компонентов и упрощает расширение системы. В отличие от полноценной Event-Driven Architecture, события существуют только в оперативной памяти в рамках одного цикла синхронизации и не сохраняются в отдельном журнале событий.

# Логирование и обработка исключений

## Общие принципы

Во всех слоях приложения используется единый подход к формированию сообщений логов и исключений.

Основная цель сообщения — максимально быстро ответить на вопросы:

* в каком компоненте произошла ошибка;
* какая операция завершилась неудачно;
* над каким объектом выполнялась операция;
* какова первопричина ошибки.

Сообщения должны описывать **операцию предметной области**, а не внутреннюю реализацию (SQL-запрос, HTTP-запрос, вызов
библиотеки и т.д.).

## Формат сообщения

Все сообщения строятся по следующему шаблону:

```text
[<Компонент>] <Описание операции> (<идентификатор1> = {}, <идентификатор2> = {}, ...): <сообщение ошибки>

```

### Примеры

```text
[ClansRepo] Failed to save clan (clan_tag = #ABC123): UNIQUE constraint failed
[RaidRepo] Failed to load raid slackers (raid_id = 15, clan_tag = #ABC123): database is locked
[APIClient] Failed to fetch endpoint (endpoint = /clans/%23ABC123): Network timeout
[ClanService] Failed to synchronize clan (clan_tag = #ABC123): Invalid clan response

```

## Компонент

Первым элементом сообщения всегда указывается источник ошибки.

Примеры компонентов:

```text
[Database]
[APIClient]
[ClansRepo]
[RaidRepo]
[ClanwarRepo]
[ClanwarsLeagueRepo]
[SubscriptionRepo]
[NotificationRepo]
[ClanService]
[RaidService]
[ClanwarService]

```

## Описание операции

Сообщение должно описывать **что именно не удалось сделать**, а не каким способом это выполнялось.

Хорошо:

```text
Failed to save clan
Failed to load players
Failed to save raid snapshot
Failed to fetch endpoint
Failed to parse response
Failed to synchronize clan

```

Плохо:

```text
INSERT failed
SELECT failed
sqlite3_step failed
HTTP 404

```

Технические детали относятся к причине ошибки, а не к описанию операции.

## Идентификаторы

После описания операции указываются только те идентификаторы, которые позволяют однозначно определить объект.

Если идентификаторов несколько, они перечисляются через запятую.

Не следует добавлять информацию, которая не помогает диагностике ошибки.

## Причина ошибки

После двоеточия всегда указывается исходная причина ошибки.

Например:

* `sqlite3_errmsg(db)`
* `e.what()`
* сообщение библиотеки CPR
* сообщение библиотеки JSON

Благодаря этому сохраняется полный контекст первопричины без потери информации.

## Исключения

Все пользовательские исключения (`DatabaseException`, `ApiException` и другие) используют тот же формат сообщений, что и
логи.

Это позволяет:

* использовать `e.what()` без дополнительного форматирования;
* логировать исключение на любом уровне приложения;
* сохранять единый стиль сообщений во всем проекте.

## Ответственность слоев

Каждый слой приложения отвечает только за свой контекст.

* **Repository** сообщает об операциях с данными.
* **APIClient** сообщает об ошибках взаимодействия с внешним API.
* **Service** сообщает об ошибках бизнес-операций.

Нижележащий слой формирует сообщение об ошибке, а вышележащий при необходимости дополняет его собственным контекстом и
повторно выбрасывает исключение.

# Текущее состояние проекта

Система поддерживает обслуживание нескольких кланов одновременно и независимую отправку уведомлений в несколько Telegram-чатов.

Архитектура построена на основе многослойного подхода с использованием репозиториев, сервисов, внутренней событийной системы (In-Memory Event System) и отдельного слоя формирования отчетов.

Каждый сервис отвечает только за получение и сохранение данных, а также генерацию доменных событий. После завершения цикла синхронизации события обрабатываются `EventDispatcher`, который передает их зарегистрированным обработчикам. На текущем этапе основным обработчиком является `NotificationService`, формирующий отчеты и отправляющий уведомления подписчикам.

Список отслеживаемых кланов и Telegram-подписок хранится в базе данных, что обеспечивает масштабируемость системы и позволяет добавлять новые кланы без изменения конфигурации приложения.

На текущем этапе управление кланами и подписками выполняется вручную через SQLite. В дальнейшем планируется реализовать полноценную систему управления через Telegram с поддержкой пользовательских настроек, подписок и дополнительных каналов доставки уведомлений.
