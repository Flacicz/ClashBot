# Clash of Clans Analytics Bot

## Общее описание

Clash of Clans Analytics Bot — это автономное серверное приложение на C++, предназначенное для автоматического сбора, хранения, анализа и уведомления о событиях в кланах Clash of Clans.

Приложение регулярно получает данные через официальный Clash of Clans API, сохраняет их в локальную SQLite базу данных, хранит историческую информацию о клане и игроках, формирует аналитические отчеты и отправляет их в Telegram.

Основная задача системы — предоставить руководству клана инструменты для контроля активности игроков, отслеживания изменений состава, анализа войн, лиги клановых войн и рейдовых выходных.

---

# Целевая аудитория

Система предназначена для:

* глав кланов;
* со-лидеров;
* ответственных за управление составом клана;
* аналитиков клановой статистики.

---

# Основной функционал

## Мониторинг клана

Система сохраняет полную историю состояния клана:

* количество участников;
* уровень клана;
* трофеи;
* очки столицы;
* параметры набора игроков;
* военную статистику;
* характеристики лиги.

Для этого используются периодические снимки состояния клана (ClanSnapshot).

---

## Мониторинг игроков

Система отслеживает:

* вступления игроков;
* выходы игроков;
* изменения роли;
* изменения уровня ратуши;
* изменения количества трофеев;
* пожертвования;
* место игрока в клане.

Для этого используются:

* Player;
* PlayerSnapshot;
* ClanMembership.

---

## История состава клана

Каждое вступление и выход игрока сохраняется в отдельную таблицу истории.

Это позволяет:

* определять новичков;
* находить ушедших игроков;
* анализировать продолжительность пребывания игроков в клане;
* строить исторические отчеты по составу.

---

## Клановые войны

Система собирает информацию о:

* регулярных войнах;
* дружественных войнах;
* войнах лиги клановых войн.

Для каждой войны сохраняются:

* информация о войне;
* информация о противнике;
* составы участников;
* все атаки;
* результаты войны.

Поддерживаются сущности:

* Clanwar;
* ClanwarClan;
* ClanwarMember;
* ClanwarAttack.

---

## Лига клановых войн (CWL)

Система сохраняет:

* сезоны CWL;
* зарегистрированных участников;
* все войны сезона;
* статистику участников.

Используются сущности:

* ClanwarsLeagueSeason;
* ClanwarsLeagueMember;
* CompleteClanwarsLeagueData.

---

## Рейд-выходные

Система сохраняет:

* информацию о рейде;
* количество проведенных атак;
* заработанную добычу;
* разрушенные районы;
* индивидуальную активность игроков.

Используются сущности:

* ClanRaid;
* PlayerRaidSnapshot.

---

## Система отчетов

На основе собранных данных формируются автоматические отчеты.

Примеры:

* игроки, покинувшие клан;
* новые участники;
* игроки, не использовавшие атаки на войне;
* игроки, не выполнившие рейдовые атаки;
* нарушения зеркальной системы атак;
* результаты завершенных войн;
* результаты CWL.

---

## Система уведомлений

Все уведомления отправляются в Telegram.

Система гарантирует, что одно и то же событие не будет отправлено повторно.

Для этого используется таблица notifications, в которой фиксируются уже обработанные события.

# Архитектура

Архитектура проекта построена по многослойному принципу.

## Domain Layer

Содержит бизнес-сущности проекта.

Основные сущности:

* Clan
* Player
* ClanSnapshot
* PlayerSnapshot
* ClanRaid
* PlayerRaidSnapshot
* Clanwar
* ClanwarClan
* ClanwarMember
* ClanwarAttack
* ClanwarsLeagueSeason
* ClanwarsLeagueMember

Агрегаты:

* CompleteClanData
* CompleteRaidData
* CompleteClanwarData
* CompleteClanwarsLeagueData

Отчетные модели:

* ClanReportData
* RaidReportData
* ClanwarReportData
* ClanwarsLeagueReportData

Каждая сущность отвечает за парсинг собственных данных из JSON через статические методы fromJson() или parse().

---

## API Layer

Центральной точкой взаимодействия с внешним API является класс APIClient.

Его задачи:

* выполнение HTTP-запросов;
* обработка ошибок сети;
* получение JSON-ответов;
* предоставление данных сервисам.

Технологии:

* CPR
* nlohmann/json

---

## Service Layer

Все сервисы наследуются от интерфейса IService.

Сервисы отвечают за:

* получение данных через APIClient;
* преобразование JSON в доменные модели;
* сохранение данных;
* возврат результатов синхронизации.

Каждый сервис изолирован и отвечает за собственную область данных:

* клан;
* войны;
* CWL;
* рейды.

---

## Repository Layer

Доступ к базе данных реализован через репозитории.

Основные репозитории:

* ClanRepository
* ClanwarRepository
* ClanwarsLeagueRepository
* RaidRepository

Репозитории инкапсулируют SQL-запросы и полностью скрывают работу с SQLite от сервисов.

---

## Database Layer

В качестве СУБД используется SQLite.

База данных содержит таблицы для:

* кланов;
* игроков;
* истории членства;
* снимков кланов;
* снимков игроков;
* войн;
* участников войн;
* атак;
* сезонов CWL;
* участников CWL;
* рейдов;
* участников рейдов;
* уведомлений.

---

## Transaction Management

Все операции записи выполняются внутри транзакций.

Для управления транзакциями используется отдельный RAII-класс TransactionGuard.

Он гарантирует:

* атомарность операций;
* автоматический rollback при ошибках;
* автоматический commit при успешном завершении.

---

## Migration System

Для управления схемой базы данных используется MigrationManager.

Он отвечает за:

* создание структуры БД;
* применение миграций;
* хранение версии схемы;
* обновление структуры базы данных между версиями приложения.

---

## Reporting Layer

Формирование отчетов реализовано через отдельный слой форматтеров.

Базовый интерфейс:

IReportFormatter

Каждый форматтер отвечает за:

* проверку необходимости отправки уведомления;
* формирование текста сообщения;
* отправку уведомления;
* регистрацию отправленного события в базе данных.

Это обеспечивает идемпотентность системы уведомлений.

---

## Notification Layer

Уведомления отделены от логики формирования отчетов.

Основные компоненты:

* NotificationService
* TelegramNotifier

NotificationService управляет процессом уведомления.

TelegramNotifier реализует доставку сообщений через Telegram Bot API.

---

# Основной цикл работы

Центральным координатором системы является ClanManager.

Каждые 30 минут запускается цикл синхронизации.

Последовательность работы:

1. ClanManager запускает сервисы.
2. Сервисы получают данные через APIClient.
3. Данные преобразуются в доменные модели.
4. Репозитории сохраняют данные в SQLite.
5. Формируются результаты синхронизации.
6. Форматтеры анализируют новые события.
7. NotificationService отправляет уведомления.
8. Информация об отправке фиксируется в таблице notifications.

# Текущее состояние проекта

На данный момент система обслуживает один клан.

Архитектура хранения данных уже позволяет поддерживать несколько кланов одновременно, однако система подписчиков и доставки уведомлений пока ориентирована на одного получателя.

В будущем возможно расширение до полноценной мультиклановой платформы с независимыми подписками, отдельными Telegram-чатами и пользовательскими настройками отчетов.
