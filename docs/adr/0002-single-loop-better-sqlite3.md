# ADR-0002: Один event loop и одно соединение `better-sqlite3`

В C++-версии ClashBot использовал четыре ОС-потока и четыре отдельных соединения SQLite (синхронизация, `DomainEventWorker`, `NotificationWorker`, `TelegramBotService`), что требовало явной синхронизации условными переменными и приводило к конкуренции за блокировки записи и гонке отмены при `/unlink`. Для TypeScript-версии мы переходим на однопоточную кооперативную модель в одном процессе Node.js.

## Решение

- **Один event loop без `worker_threads`**: все четыре фоновых цикла (`ClanManager`, `DomainEventWorker`, `NotificationWorker`, `TelegramBotService`) работают кооперативно на `async/await` в одном процессе Node.js. После коммита материализации доменного события `DomainEventWorker` немедленно пробуждает `NotificationWorker`.
- **Одно общее соединение `better-sqlite3`**: приложение открывает одно соединение SQLite с параметрами `PRAGMA foreign_keys = ON`, `PRAGMA journal_mode = WAL`, `PRAGMA synchronous = NORMAL` и `PRAGMA busy_timeout = 5000`.
- **Синхронные транзакции `BEGIN IMMEDIATE`**: все записывающие операции сервисов синхронизации, команд `/link` / `/unlink`, материализации доменных событий и миграций выполняются через `TransactionManager` в синхронных транзакциях `BEGIN IMMEDIATE` с повтором при `SQLITE_BUSY` (до 3 попыток с задержкой 100 мс) для безопасного сосуществования с внешними процессами (например, онлайн-бэкапом SQLite).
- **Гарантия инварианта «Чистые транзакции»**: так как транзакции `better-sqlite3` строго синхронны, `await` внутри транзакции невозможен на уровне API. Внешние HTTP-запросы к Clash of Clans API и Telegram Bot API гарантированно выполняются только вне транзакций SQLite.
- **Перепроверка статуса `pending` перед обработкой**:
  - в `DomainEventWorker` внутри синхронной транзакции перед материализацией получателя события перепроверяется, что строка в `domain_event_destinations` всё ещё имеет статус `pending`;
  - в `NotificationWorker` непосредственно перед HTTP-вызовом отправки уведомления перепроверяется, что строка в `notifications` всё ещё имеет статус `pending`.
  Это закрывает гонку отмены через `/unlink` для записей, уже попавших в загруженную пачку, без изменения схемы БД.
- **Единый `AbortController` и `ShutdownCoordinator`**: при получении `SIGINT` или `SIGTERM` единый `AbortController` одновременно отменяет активные HTTP-запросы, прерываемые таймеры ожидания и long polling `grammY`, а `ShutdownCoordinator` ограничивает общее ожидание завершения всех циклов бюджетом **15 секунд** (с запасом до `stop_grace_period: 30s` в `docker-compose.yml`). Прерывание по остановке не сжигает `attempts` у получателей событий и уведомлений и не открывает ложные эпизоды `sync_outages`.

## Рассмотренные альтернативы

- **Использование `worker_threads` и нескольких соединений SQLite по аналогии с C++**: отклонено, так как нагрузка ClashBot ограничена сетевым I/O (цикл синхронизации раз в 15 минут, редкие уведомления и команды Telegram), а `worker_threads` добавляют сложность сериализации сообщений, координации остановки и конкуренции за блокировки SQLite без выигрыша в производительности.
- **Асинхронные драйверы SQLite (`sqlite3` / `libsql`)**: отклонены, поскольку позволяют случайно вставить `await` с HTTP-запросом внутрь открытой транзакции и ослабляют гарантию атомарности без блокировки записи.

## Последствия

- Короткие синхронные SQLite-операции выполняются за микросекунды и не блокируют event loop на заметное время; долгие операции (HTTP-запросы к CoC API и Telegram) всегда асинхронны и прерываемы через `AbortSignal`.
- Модель рассчитана на один активный экземпляр ClashBot на один файл SQLite (без многоэкземплярного lease/claim-механизма).
- Как и в C++-версии, доставка уведомлений сохраняет семантику at-least-once: если процесс аварийно остановится после успешного ответа Telegram, но до `markAsSent`, возможна повторная отправка. Отмена `/unlink` в SQLite не отзывает уже отправленный HTTP-запрос, но исключает старт отправки уже отменённых строк из пачки.
