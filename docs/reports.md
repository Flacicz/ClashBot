# Reporting Layer

## Общее описание

Reporting Layer отвечает за преобразование доменных событий в пользовательские отчеты, предназначенные для отправки в Telegram.

После внедрения внутренней Event System слой отчетов больше не участвует в анализе изменений и не принимает решений о необходимости отправки уведомлений.

Его единственная ответственность — сформировать человекочитаемый отчет на основе полученного события и данных, сохраненных в базе данных.

---

# Поток формирования отчета

После завершения синхронизации сервисы возвращают список обнаруженных Domain Events.

Далее события проходят следующий путь:

```
Service
        ↓
Domain Event
        ↓
SyncResult.events
        ↓
EventDispatcher
        ↓
NotificationService
        ↓
Report Formatter
        ↓
TelegramNotifier
```

Каждый этап отвечает только за собственную область ответственности и не знает о деталях работы остальных компонентов.

---

# Domain Events

Domain Events описывают факт произошедшего изменения в системе.

Примеры событий:

* PlayerJoinedClanEvent
* PlayerLeftClanEvent
* PlayerRoleChangedEvent
* WarEndedEvent
* WarReminderEvent
* RaidReminderEvent
* ClanwarsLeagueRoundEndedEvent
* RaidsEndedEvent
* SyncFailureEvent
* SyncRecoveryEvent

События содержат только минимальный набор данных, необходимый для идентификации произошедшего изменения.

Например:

* тег клана;
* идентификатор войны;
* время окончания войны;
* тип временной контрольной точки для `WarReminderEvent`;
* идентификатор рейда;
* тег игрока;
* старая и новая роль.

Это позволяет сервисам не заниматься подготовкой отчетов и не выполнять дополнительные запросы к базе данных.

# Report Formatters

Для каждого типа отчёта используется собственный форматтер. Одно событие может запускать несколько форматтеров.

На текущий момент реализованы:

* ClanwarEndedFormatter
* ClanwarsLeagueRoundEndedFormatter
* PlayerJoinedFormatter
* PlayerLeftFormatter
* PlayerRoleChangedFormatter
* RaidsEndedFormatter
* RaidsComparisonFormatter
* RaidsViolationsFormatter
* WarReminderFormatter
* RaidReminderFormatter
* ClanwarViolationsFormatter
* ClanwarsLeagueRoundViolationsFormatter
* ClanwarComparisonFormatter
* ClanwarRosterFormatter
* SystemAlertReportFormatter

Каждый форматтер отвечает только за один тип события.

`ClanwarEndedFormatter` и `ClanwarsLeagueRoundEndedFormatter` используют общие функции из `WarReportParts`. Они формируют
результат войны или раунда, статистику атак и лучшие атаки, но не включают списки нарушений. `RaidsEndedFormatter`
показывает общую статистику рейда и лучших участников. `RaidsComparisonFormatter` формирует сравнительный отчёт
последнего рейда относительно предыдущего рейда и среднего значения максимум трёх предыдущих рейдов.

Списки нарушений вынесены в отдельные форматтеры для управленческой аудитории:

* `ClanwarViolationsFormatter` показывает игроков без атак, игроков ровно с одной атакой и первые атаки не по зеркалу;
* `ClanwarsLeagueRoundViolationsFormatter` показывает пропущенные атаки и первые атаки не по зеркалу в раунде CWL;
* `RaidsViolationsFormatter` показывает игроков, которые не использовали все доступные рейдовые атаки, включая отдельную
  категорию игроков без атак.

Для рейдов доступный лимит рассчитывается индивидуально: `5 + bonus_attacks`. Игроки, покинувшие клан до окончания
рейдовых выходных, в список нарушений не попадают.

`SystemAlertReportFormatter` формирует сообщения о сбое синхронизации и восстановлении сервиса. В отличие от остальных
форматтеров, ему не нужны дополнительные запросы к репозиториям.

`WarReminderFormatter` формирует короткие сообщения для временных контрольных точек обычной клановой войны. Форматтер
получает из события тег клана, время окончания войны и тип напоминания, поэтому ему не требуется обращение к репозиторию.

Поддерживаются три типа напоминаний:

* начало войны;
* 6 часов до окончания;
* 1 час до окончания.

`RaidReminderFormatter` формирует сообщения для общего Telegram-чата участников рейдовых выходных. Поддерживаются пять
контрольных точек: начало, 48 часов, 24 часа, 6 часов и 1 час до окончания.

`WarReminderFormatter` также формирует отдельные варианты сообщений для раундов CWL. Для CWL используются три
контрольные точки: начало раунда, 6 часов до окончания и 1 час до окончания. Форматтер выбирает текст по полю типа
войны в `WarReminderEvent`, сохраняя общий механизм доставки и дедупликации.

# Развитие информативности отчётов

Последнее обновление разделило отчёты о завершённых событиях на пользовательские сводки и отдельные управленческие отчёты
о нарушениях. Благодаря этому игроки видят общий результат и вклад участников, а руководство получает детальный список
проблемных случаев.

| Отчёт | Раньше | Сейчас |
|---|---|---|
| Война кланов | Результат, звёзды, процент разрушения и списки нарушений в одном сообщении | Отчёт для игроков: результат, использованные атаки, средние звёзды и разрушение за атаку, распределение результатов от 0 до 3 звёзд и лучшие атаки; отдельный отчёт для руководства: пропуски, игроки с одной атакой и атаки не по зеркалу |
| Раунд CWL | Результат раунда, пропущенные атаки и нарушения зеркальной системы в одном сообщении | Отчёт для игроков: результат раунда, статистика атак и лучшие атаки; отдельный отчёт для руководства: пропущенные атаки и атаки не по зеркалу |
| Рейд выходного дня | Только игроки, сделавшие не все атаки или не атаковавшие вообще; лимит считался фиксированным `6/6` | Отчёт для игроков: общая добыча, завершённые рейды, число атак, уничтоженные районы, наступательная и оборонительная награды и лучшие участники; сравнительный отчёт с предыдущим рейдом и историческим средним; отдельный отчёт для руководства: неиспользованные атаки с лимитом `5 + бонусные атаки` |

Сравнительный отчёт обычной войны показывает показатели в нормализованном виде, чтобы размер команды не искажал
сравнение: долю использованных атак, долю игроков без атак и долю первых атак не по зеркалу. Долю игроков с одной
атакой отчёт показывает отдельно как показатель активности: сама по себе неиспользованная вторая атака не является
нарушением, поскольку она может быть не нужна после успешной первой атаки. Абсолютные значения остаются в скобках
как дополнительный контекст.

В заголовке сравнительного отчёта последняя война обозначается как завершённая (`Последняя война`), а для последней
и предыдущей войн выводятся названия и теги домашнего клана и соперника.

Итоговый тренд рассчитывается по четырём основным метрикам: средние звёзды за атаку, разрушение, доля игроков без атак
и доля первых атак не по зеркалу. Использование атак, доля игроков с одной атакой и общее число пропущенных атак
выводятся отдельно как показатели активности и не учитываются в итоговой оценке. Отчёт показывает количество и процент
улучшившихся, ухудшившихся и неизменившихся основных метрик.

Для прямого сравнения берутся последняя и предыдущая завершённые обычные войны. Историческая секция использует среднее
значение максимум трёх предыдущих обычных войн. Средние звёзды и среднее разрушение за атаку рассчитываются с учётом
количества использованных атак. Долевые показатели рассчитываются как отношение суммы числителей к сумме знаменателей,
поэтому составы разного размера не искажают сравнение. Средние абсолютные значения отображаются отдельно как контекст.

Сравнительный отчёт рейдов построен по той же структуре, что и сравнительный отчёт обычной войны: сначала показывается
сравнение с предыдущим рейдом, затем — сравнение со средним максимум за три предыдущих рейда. Если предыдущий рейд
отсутствует, отчёт не формируется; если исторических рейдов нет, исторический блок и итоговая оценка не выводятся.

В отчёте рейдов используются следующие показатели:

* добыча на использованную атаку;
* полностью использованные доступные атаки среди активных участников;
* использовали не все атаки среди активных участников;
* участники без атак среди всех подходящих участников;
* использование атак и доля активных участников — в блоке активности;
* итоговые показатели рейда: добыча, завершённые рейды, уничтоженные районы и награды.

Активным участником рейда считается игрок, присутствующий в API-ответе, то есть сделавший хотя бы одну атаку.
Подходящие участники включают активных игроков и игроков без атак. Показатели дисциплины и активности выводятся
в виде долей, а рядом показываются абсолютные значения. Итоговая оценка рейда строится по трём основным метрикам:
добыча на использованную атаку, полное использование атак среди активных участников и доля участников без атак.
Использование атак и активные участники остаются справочными показателями и в итоговую оценку не входят.

Для исторических рейдов долевые метрики считаются взвешенно: суммируются числители и знаменатели всех рейдов периода,
после чего вычисляется единая доля. Это сохраняет согласованность процента с отображаемой дробью и корректно учитывает
разное количество участников и доступных атак.

Для лучших атак и нарушений зеркальной системы теперь выводятся позиции атакующего и цели. Поэтому сообщение показывает
не только имя нарушителя, но и направление атаки (`№ атакующего → № цели`).

Уведомления об изменении состава и ролей также получили единый формат: название и тег клана, имя и тег игрока, а для
изменения роли — старое и новое значения. Системные сообщения о сбое и восстановлении синхронизации переведены на русский
язык и явно указывают клан и сервис.

Расчёт статистики выполняется репозиториями, а общие части военных отчётов формируются через `WarReportParts`. Это сохраняет
одинаковую структуру обычных войн и CWL и не перегружает форматтеры вычислениями. Отчёты о результате, сравнении и
напоминаниях отправляются игрокам, а нарушения, надёжность состава и системные сообщения — руководству.

# Ответственность форматтеров

Форматтер выполняет следующие задачи:

* получает Domain Event;
* при необходимости запрашивает дополнительные данные через репозитории;
* формирует готовый текст отчета;
* возвращает сформированное сообщение вызывающему коду.

Форматтер не:

* определяет необходимость отправки уведомления;
* взаимодействует с Telegram API;
* хранит информацию об уже отправленных уведомлениях;
* изменяет состояние базы данных.

---

# NotificationService

NotificationService является координатором слоя отчетов.

Для каждого полученного Domain Event он:

1. определяет тип события через `std::visit`;
2. вызывает соответствующий Report Formatter;
3. получает готовый текст отчета;
4. определяет аудиторию сообщения и получает из `SubscriptionRepo` список подписчиков клана для этой аудитории;
5. отправляет сообщение каждому подписанному Telegram-назначению, передавая `chat_id` и `message_thread_id`;
6. для завершённых войн, раундов CWL, рейдов и временных напоминаний проверяет и фиксирует событие в таблице
   `notifications`, не допуская повторной отправки одному и тому же чату или теме.

Поддерживаются две аудитории подписок:

* `players` — изменения состава и ролей, отчёты о результатах, сравнительные отчёты и временные напоминания;
* `management` — отчёты о нарушениях, отчёт о надёжности состава и системные сообщения.

Один Domain Event может запускать несколько независимых отправок. Например, `WarEndedEvent` формирует отчет о результате
и сравнительный отчет для `players`, а отчет о нарушениях и отчет о надежности состава — для `management`. `RaidsEndedEvent`
формирует для `players` обычный отчёт по рейду и сравнительный отчёт, а для `management` — отчёт о нарушениях.

Для обычного и сравнительного отчёта рейда используются разные типы отправки (`raids_ended` и `raids_comparison`),
поэтому дедупликация позволяет независимо доставить оба сообщения одному Telegram-назначению.

Для `WarReminderEvent` и `RaidReminderEvent` ключ отправки содержит идентификатор события и контрольную точку:

```text
war_reminder | 42:started        | chat_id | message_thread_id
war_reminder | 42:six_hours_left | chat_id | message_thread_id
war_reminder | 42:one_hour_left  | chat_id | message_thread_id
raid_reminder | 15:started       | chat_id | message_thread_id
raid_reminder | 15:twenty_four_hours_left | chat_id | message_thread_id
raid_reminder | 15:six_hours_left       | chat_id | message_thread_id
raid_reminder | 15:one_hour_left        | chat_id | message_thread_id
```

Напоминания создаются сервисами `ClanwarService`, `ClanwarLeagueService` и `RaidService`, когда текущее время достигает
соответствующей контрольной точки.
Фактическая доставка зависит от интервала синхронизации: при текущем цикле в 30 минут сообщение может прийти с задержкой
до одного цикла.

# Архитектурные преимущества

Текущая архитектура обладает рядом преимуществ:

* сервисы полностью отделены от логики формирования отчетов;
* каждый форматтер отвечает только за один тип события;
* форматтеры легко тестируются независимо друг от друга;
* NotificationService не содержит логики построения сообщений;
* добавление нового типа уведомления не требует изменения сервисов синхронизации, кроме генерации нового события;
* система соответствует принципу Single Responsibility Principle (SRP).

---

# Расширяемость

Для добавления нового отчета требуется выполнить следующие шаги:

1. создать новый Domain Event;
2. сгенерировать событие в соответствующем сервисе;
3. реализовать новый Report Formatter;
4. добавить событие в `ApplicationEvent`;
5. зарегистрировать его обработку в `NotificationService`.

При этом существующие форматтеры не требуют изменения своей внутренней логики.

# Future Evolution

Система отчетности проектируется как расширяемый модуль.

Планируемые направления развития:

* пользовательские настройки уведомлений;
* подписки на отдельные категории отчетов;
* отключение отдельных типов уведомлений;
* гибкое расписание отчетов;
* пользовательские настройки временных уведомлений;
* экспорт отчетов в CSV;
* экспорт отчетов в Excel;
* веб-панель аналитики;
* графики активности игроков;
* расширение исторических сравнительных отчетов и аналитики игроков;
* система рекомендаций для управления составом.

В долгосрочной перспективе отчетность должна стать основным инструментом аналитики и управления кланом.
