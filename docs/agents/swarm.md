# Оркестрация Swarm

Регламент мультиагентных сессий `/swarm`. Правила веток, интеграционных PR и миграций вынесены в [`git-workflow.md`](git-workflow.md); общие инварианты и Definition of Done — в [`AGENTS.md`](../../AGENTS.md).

## Роли и модели по умолчанию

| Роль | Модель | `workspace` | Ответственность |
| --- | --- | --- | --- |
| **Координатор** | Текущая модель чата | Основной (`<wave-branch>`) | Ведёт волну, инварианты, ревью-гейт, squash-вливание в `<wave-branch>` и финальный PR техлиду; продуктовый код не пишет |
| **Кодер** | `Gemini 4 Neon (High)` (`gemini-4-neon-high`) | `share` | Изолированная ветка на один тикет: код, тесты, документация, прогон проверок |
| **Ревьюер** | `Gemini 4 Hydrogen (High)` (`gemini-4-hydrogen-high`) | `inherit` (строгий read-only) | Двухосевой аудит диффов (`Spec` + `Standards`) без правок файлов и без переключения веток в общем рабочем дереве |

- При сомнении в доступности моделей перед стартом волны проверь `swarm(action="models", all=true)`.
- При исчерпании квоты переключай ожидающего воркера через `swarm(action="model")` с указанием причины (не используй `kill` + `add` ради смены модели).

## Планирование волн и параллелизм

- Держи в работе одновременно **2–3 независимых тикета**.
- **Сериализация зависимостей:**
  - тикеты с новыми SQL-миграциями выполняются строго последовательно — следующий стартует от обновлённой `origin/<wave-branch>` после вливания предыдущего;
  - тикеты с пересечением общих файлов либо запускаются последовательно, либо второй подтягивает обновлённую `<wave-branch>` через `git merge` и проходит повторное ревью после вливания первого.

## Бриф кодеру

Передавай в брифе указатели контекста без пересказа спецификации:

- номер тикета и обязательное чтение полного описания с комментариями триажа (`gh issue view <n> --comments`);
- базовую ветку (`origin/<wave-branch>`), имя рабочей ветки тикета и номер SQL-миграции (либо `0 миграций`);
- обязательное чтение `AGENTS.md`, `docs/agents/git-workflow.md` и релевантных документов из карты `docs/`;
- требование выполнить проверки из `AGENTS.md` и по готовности написать на доску с упоминанием `@reviewer` и `@coordinator` (имя ветки/коммит, краткое резюме и результаты проверок).

## Двухосевой Review Gate

`@reviewer` проверяет каждую ветку тикета в режиме read-only (`git fetch origin`, `git diff origin/<wave-branch>...origin/<ticket-branch>`, `git show`, `gh issue view <n> --comments`) по двум осям:

1. **Spec** — строгое соответствие телу тикета, решениям из комментария триажа и всем краевым случаям.
2. **Standards** — инварианты и DoD из `AGENTS.md`, неизменность применённых миграций, чек-лист миграций и Docker smoke-теста из `git-workflow.md`, покрытие тестами, актуальная документация и Conventional Commits.

Отчёт ревьюера завершается однозначным вердиктом: `APPROVE` или `CHANGES_REQUESTED` с конкретными файлами и строками.

- **Лимит итераций:** до 2 раундов правок (итого до 3 прогонов ревью) на тикет. Если блокеры не сняты или обнаружена неоднозначность спецификации / расхождение кода с документацией — останови тикет и эскалируй человеку.

## Жизненный цикл воркеров и Swarm UI

- Поддерживай `plan.json` в актуальном состоянии согласно навыку `swarm_pane` при старте волны и изменении состава.
- Завершай (`swarm(action="kill")`) отработавшего кодера сразу после вливания его ветки в `<wave-branch>` (или после merge отдельного PR в `main`).
- По завершении волны и закрытии/передаче финального PR завершай всех оставшихся воркеров.
