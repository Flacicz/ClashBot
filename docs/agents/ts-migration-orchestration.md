# Автономная оркестрация переноса на TypeScript (`#16`, тикеты `#17`–`#35`)

> Исторический регламент side-by-side переноса. Актуальный рабочий процесс описан в [AGENTS.md](../../AGENTS.md).

Регламент для автономного оркестратора (Swarm в Antigravity), выполняющего side-by-side перенос ClashBot с C++20 на TypeScript поверх спецификации `#16`.

## Область действия и стоп-краны

- **Разрешённый контур**: только тикеты `#17`–`#35` (помеченные `ready-for-agent`, родитель `#16`), выполняемые в интеграционной ветке `feat/ts-migration` от `origin/main`.
- **Неприкосновенность C++ и прода**: C++-исходники, CMake/vcpkg, существующий C++ `Dockerfile`, `.github/workflows/ci.yml`, `.github/workflows/docker-publish.yml`, применённые миграции `src/database/migrations/001..012` и баги `#1`–`#8` остаются без изменений в `git diff`.
- **Секреты и прод**: чтение и изменение `.env`, `config.json`, `data/`, реальных токенов, продовой SQLite-базы и реальных Telegram-чатов запрещены (правило из `AGENTS.md` действует без исключений).
- **Плановые стоп-краны (решает только человек)**:
  1. Слияние итогового PR `feat/ts-migration` → `main` после `#35`.
  2. Тикет `#36` (`T5.2`, `ready-for-human` — пробный прогон на копии продовой БД и тег `v1-cpp`).
  3. Слияние Cutover-PR `#37` (`T5.3`).

## Роли и модели Swarm

Каждый тикет обрабатывают **одноразовые воркеры** с чистым контекстом: воркер создаётся через `swarm(action="add")` под один тикет и удаляется через `swarm(action="kill")` сразу после вливания ветки тикета в `feat/ts-migration`.

| Роль | Модель | Когда применять | Workspace |
| --- | --- | --- | --- |
| **Оркестратор** (координатор) | `Orchestrator (Neon)` (`gemini-pro-orchestrator-neon`) | Главный чат, ведёт граф задач, мержи и эскалацию | Основной (`feat/ts-migration`) |
| **Кодер (типовой тикет)** | `Gemini 4 Neon (Medium)` (`gemini-4-neon-medium`) | `#17`, `#18`, `#20`, `#21`, `#22`, `#24`, `#26`, `#27`, `#28`, `#29`, `#30`, `#32`, `#35` | `workspace: "share"` |
| **Кодер (сложный тикет)** | `Gemini 4 Neon (High)` (`gemini-4-neon-high`) | `#19`, `#23`, `#25`, `#31`, `#33`, `#34` | `workspace: "share"` |
| **Независимый ревьюер (типовой)** | `Gemini 4 Argon (Medium)` (`gemini-4-argon-medium`) | 1 свежий воркер на тикет, проверяет обе оси ревью (отдельный бакет квоты на Pro; резерв при исчерпании — `Gemini 4 Hydrogen (High)`) | `workspace: "inherit"` (или чтение ветки тикета) |
| **Независимый ревьюер (сложный / арбитр)** | `Gemini 4 Argon (High)` (`gemini-4-argon-high`) | Сложные тикеты (`#19`, `#23`, `#25`, `#31`, `#33`, `#34`) и повторное ревью при спорных блокерах после 1-го раунда правок | `workspace: "inherit"` |
| **Быстрый поиск / сверка C++-эталона** | `Gemini 4 Hydrogen (Low)` / `(Medium)` (`gemini-4-hydrogen-low` / `gemini-4-hydrogen-medium`) | Опционально, когда нужно собрать карту файлов/контрактов C++ для нескольких параллельных тикетов | `workspace: "inherit"` |

- **Управление квотой**: при исчерпании квоты модели оркестратор переключает ожидающего воркера через `swarm(action="model")` на резервную модель (`Argon` ↔ `Hydrogen`/`Neon`, никогда не `kill` + `add` ради смены модели) и отмечает переключение в логе.
- **Параллелизм**: одновременно в работе не более **2–3 независимых тикетов** из текущего фронта DAG.

## Подготовка перед стартом (Pre-flight)

Выполнить один раз до первого тикета:

1. Убедиться, что на машине активирован `pnpm` (если команда `pnpm --version` недоступна, выполнить `corepack enable`).
2. Синхронизировать `origin/main` (`git fetch origin main`).
3. Создать или переключиться на ветку `feat/ts-migration` от `origin/main` и запушить её (`git push -u origin feat/ts-migration`).
4. Убедиться, что рабочее дерево чистое (`git status --short` пуст).

**Критерий готовности шага**: `pnpm --version` возвращает версию, текущая ветка — `feat/ts-migration`, `git status --short` пуст.

## Цикл оркестрации по графу задач (DAG)

Повторять до закрытия всех тикетов `#17`–`#35`:

### Шаг 1. Определить фронт готовых тикетов

Запросить открытые тикеты `#17`–`#35` с меткой `ready-for-agent` и оставить те, у которых нет открытых блокеров (`blockedBy` со статусом `OPEN` пуст) и нет активного воркера:

```powershell
$issues = gh issue list --state open --label ready-for-agent --limit 40 --json number,title,blockedBy | ConvertFrom-Json
$issues | Where-Object {
  $_.number -ge 17 -and $_.number -le 35 -and
  (@($_.blockedBy.nodes | Where-Object { $_.state -eq "OPEN" }).Count -eq 0)
} | Sort-Object number | Select-Object number, title
```

Если фронт пуст и все `#17`–`#35` закрыты → перейти к разделу «Финальная сдача после `#35`».
Если фронт пуст, но остались открытые тикеты из `#17`–`#35` (например, после эскалации) → остановиться и доложить человеку.

### Шаг 2. Запустить до 2–3 кодеров в изолированных `workspace: "share"`

Для каждого выбранного тикета `#N`:

1. Назначить имя воркера `coder-N` и ветку `ts/t-<N>`.
2. В брифе передать только **указатели контекста** (без пересказа спецификации):
   - номер и цель тикета `#N` (`gh issue view N`), родитель `#16`;
   - обязательное чтение `GLOSSARY.md` и `docs/adr/0001..0004` (как только `#17` влит);
   - ветку-базу `feat/ts-migration` (воркер создаёт ветку `ts/t-<N>` от текущего `HEAD` ветки `feat/ts-migration`);
   - требование писать код через TDD, соблюдать инварианты из `AGENTS.md` и `ADR-0001..0004`, и оставить C++-файлы без изменений;
   - особые правила тикета из раздела «Особые правила для отдельных тикетов» ниже;
   - список обязательных локальных проверок до сдачи.

**Критерий готовности кодера**: ветка `ts/t-<N>` содержит коммиты с реализацией и тестами, все жёсткие проверки зелёные, `git diff --name-only feat/ts-migration...HEAD` не затрагивает запрещённые C++/продовые файлы, воркер отчитался оркестратору с перечнем изменённых файлов и выводами команд проверки.

### Шаг 3. Проверить жёсткий Quality Gate

Перед вызовом ревьюера оркестратор убеждается, что выполнены все применимые проверки:

- для `#17` (только документация/ADR): `git diff --check`, терминология соответствует `GLOSSARY.md`, все 4 ADR на месте, C++-файлы не изменены;
- начиная с `#18`:
  - `pnpm typecheck` (`tsc --noEmit`),
  - `pnpm lint` (ESLint),
  - `pnpm format:check` (Prettier),
  - `pnpm test` (все unit, integration и golden-тесты Vitest),
  - `git diff --check`,
  - `git diff --name-only feat/ts-migration...HEAD` не содержит изменений в C++-исходниках, CMake/vcpkg, C++ `Dockerfile`, `.github/workflows/ci.yml`, `.github/workflows/docker-publish.yml` и `src/database/migrations/`.

Если хотя бы одна проверка падает — вернуть кодеру на исправление (без запуска ревьюера).

### Шаг 4. Независимое двух-осевое ревью в чистом контексте

Создать нового одноразового воркера `reviewer-N` (не форкать контекст кодера!) с моделью из таблицы выше. Передать ему:
- команду для просмотра диффа `git diff feat/ts-migration...ts/t-<N>` и список коммитов;
- ссылку на тикет `#N`, спецификацию `#16`, `GLOSSARY.md` и `docs/adr/`;
- требование выдать отчёт строго по **двум отдельным осям** и завершить однозначным вердиктом `APPROVE` или `CHANGES_REQUESTED`:
  1. **`Spec & C++ Parity`**:
     - каждый пункт Acceptance Criteria тикета `#N` выполнен полностью;
     - логика, граничные случаи, строковые контракты БД и форматы вывода совпадают с эталонным C++-кодом и `ADR-0001..0004`;
     - отсутствует scope creep и правки C++/продовых файлов.
  2. **`Standards & Invariants`**:
     - транзакции SQLite чистые (нет внешних HTTP-вызовов внутри транзакции);
     - сохранена атомарность событий и идемпотентность outbox;
     - тесты покрывают штатный, граничный/ошибочный и повторный сценарии без подгонки тестов под дефекты;
     - нет критичных дефектов дизайна или необработанных ошибок.

**Лимит итераций**:
- При `CHANGES_REQUESTED` оркестратор передаёт список блокеров обратно `coder-N`, после фикса заново проверяет Шаг 3 и запускает повторное ревью (при спорных блокерах после 1-го раунда правок — на `Gemini 4 Argon (High)`).
- Допускается максимум **2 раунда правок** (итого до **3 прогонов ревью**) на один тикет.
- Если после 2-го раунда правок вердикт всё ещё `CHANGES_REQUESTED` — **не мержить**. Перевести тикет в эскалацию (см. раздел «Эскалация человеку»).

### Шаг 5. Вливание в `feat/ts-migration`, пуш и закрытие тикета

После вердикта `APPROVE`:

1. Если `feat/ts-migration` успела продвинуться вперёд за время работы тикета — в worktree кодера `coder-N` подтянуть свежую базу (`git merge feat/ts-migration`) и повторно прогнать жёсткие проверки из Шага 3.
2. В основном workspace на `feat/ts-migration` выполнить squash-слияние `ts/t-<N>` в 1 чистый коммит по Conventional Commits (с указанием номера тикета, например `feat(ts): implement sqlite layer and migrator (#19)`): `git merge --squash ts/t-<N> && git commit -m "..."`.
3. Выполнить `git push origin feat/ts-migration`.
4. Удалить воркеров `coder-N` и `reviewer-N` через `swarm(action="kill")` (это удалит временный worktree `share`), затем при необходимости удалить временную локальную ветку `git branch -D ts/t-<N>`.
5. Опубликовать в тикете `#N` краткий комментарий (SHA коммита в `feat/ts-migration`, прогнанные проверки, итог двух-осевого ревью) и закрыть issue:

```powershell
gh issue comment <N> --body "..."
gh issue close <N>
```

**Критерий готовности шага**: коммит запушен в `origin/feat/ts-migration`, `gh issue view <N> --json state` возвращает `CLOSED`, воркеры тикета завершены.

## Особые правила для отдельных тикетов

- **`#17` (`T0.1`)**: создаёт `docs/adr/0001..0004`. Все последующие кодеры и ревьюеры обязаны сверяться с этими четырьмя ADR как с источником истины.
- **`#18` (`T0.2`)**: новый GitHub Actions workflow для TypeScript (`ts-ci.yml`) должен запускаться на `pull_request` в `main`, `push` в `main` **и `push` в `feat/ts-migration`**, чтобы на каждом влитом тикете проверялась сборка под Linux (`better-sqlite3`, регистр путей, тесты).
- **`#27`, `#28`, `#29`, `#30` (golden-тесты) и `#34` (drop-in БД v012)**: кодер может локально запускать существующую C++-сборку (или временный локальный тест/утилиту вне коммита) для снятия эталонных HTML-снапшотов и генерации тестовой SQLite-базы v012. Перед коммитом любые временные артефакты вне TS-фикстур удаляются — `git diff` по C++-коду должен оставаться пустым.
- **`#35` (`T5.1`)**: локально проверить сборку TS Docker-образа (`docker build`), не изменяя продовый C++ `Dockerfile` и `.github/workflows/docker-publish.yml`.

## Эскалация человеку

Оркестратор **немедленно останавливает проблемный тикет** (не форсируя мерж) и пишет человеку структурированный отчёт, если:
- исчерпан лимит 2 раундов правок (3 прогона ревью без `APPROVE`);
- обнаружено противоречие между спецификацией `#16`, C++-кодом и документацией, требующее доменного решения;
- упал CI в `origin/feat/ts-migration` по системной причине среды/инфраструктуры, которую нельзя починить в рамках тикета;
- исчерпаны квоты всех подходящих моделей.

Формат эскалации: номер тикета и ветка `ts/t-<N>`, суть блокера со ссылками на файлы/строки, что уже пробовали (раунды правок), конкретный вопрос/выбор для человека. Независимые тикеты, не заблокированные этим тикетом, можно довести до сдачи перед паузой, если проблема локальна.

## Финальная сдача после `#35`

Когда все тикеты `#17`–`#35` закрыты:

1. Прогнать полный набор проверок на финальном `HEAD` ветки `feat/ts-migration` (`pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm test`, `git diff --check`, проверка отсутствия правок в C++-коде).
2. Проверить статус последнего запуска `ts-ci.yml` на `origin/feat/ts-migration`.
3. Открыть **один итоговый PR** `feat/ts-migration` → `main` (без автомержа!), указав в описании ссылку на `#16`, список закрытых тикетов `#17`–`#35`, прогнанные проверки, ключевые инварианты и остаточные риски.
4. Дождаться завершения всех обязательных GitHub Actions проверок на PR (4 C++ чека + TS CI). Если упал какой-либо чек — исправить и запушить фикс в `feat/ts-migration`.
5. Остановиться и передать PR человеку со сводкой: **«PR готов к вашему Merge в `main`, следующий шаг — ручной тикет `#36` (Dress Rehearsal)»**.
