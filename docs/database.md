# Database

## Общее описание

В качестве СУБД проект использует SQLite.

База данных хранит как текущее состояние кланов, так и исторические данные, необходимые для построения аналитики и формирования отчетов.

Структура базы данных разделена на несколько логических областей:

* информация о кланах и игроках;
* исторические снимки состояния;
* история членства игроков;
* клановые войны;
* лига клановых войн (CWL);
* рейд-выходные;
* система подписок Telegram;
* журнал отправленных уведомлений.

Практически все данные привязаны к конкретному клану через `clan_tag`, что позволяет системе одновременно обслуживать несколько независимых кланов.

---

# Основные таблицы

## Кланы

### clans

Хранит основную информацию о каждом отслеживаемом клане.

Каждая запись представляет отдельный клан, обслуживаемый системой.

Используется как центральная таблица, на которую ссылаются остальные сущности.

---

## Игроки

### players

Содержит текущую информацию об игроках.

Игрок существует независимо от членства в конкретном клане и может переходить между различными кланами.

---

### clan_memberships

Хранит полную историю пребывания игроков в кланах.

Для каждого периода членства сохраняются:

* время вступления;
* время выхода.

Если поле `left_at` равно `NULL`, игрок в настоящий момент находится в клане.

Эта таблица позволяет строить историческую аналитику состава клана без потери данных.

---

## История состояния

### clan_snapshots

Периодические снимки состояния клана.

Используются для хранения истории изменения:

* количества участников;
* уровня клана;
* военной статистики;
* требований к вступлению;
* характеристик столицы;
* прочих параметров клана.

---

### player_snapshots

Периодические снимки состояния игроков.

Используются для анализа изменения:

* роли;
* уровня ратуши;
* количества трофеев;
* пожертвований;
* положения в клане;
* других игровых характеристик.

История не удаляется даже после выхода игрока из клана.

# Клановые войны

## wars

Хранит информацию обо всех войнах.

Поддерживаются:

* обычные войны;
* войны CWL;
* дружественные войны.

---

## war_clans

Информация об обеих сторонах войны.

Для каждой войны сохраняются:

* домашний клан;
* противник;
* итоговые звезды;
* процент разрушений;
* количество атак.

---

## war_members

Состав участников войны.

Хранится:

* игрок;
* номер базы;
* уровень ратуши;
* принадлежность стороне войны.

---

## attacks

Все атаки каждой войны.

Позволяет выполнять детальную аналитику:

* пропущенные атаки;
* зеркальные атаки;
* эффективность игроков;
* статистику по базам.

---

# Лига клановых войн (CWL)

## cwl_seasons

Информация о сезонах CWL.

---

## cwl_season_members

# Рейд-выходные

## clan_raids

Содержит информацию о каждом рейде:

* время начала;
* время окончания;
* состояние рейда;
* общий объем добычи;
* количество атак;
* количество разрушенных районов;
* итоговые награды.

---

## player_raid_snapshots

Индивидуальная статистика участников рейда.

Используется для анализа активности игроков во время рейдовых выходных и формирования сравнительных отчетов.

Для этих отчетов активными считаются игроки, присутствующие в API-ответе рейда, то есть выполнившие хотя бы одну атаку.
Подходящие участники дополнительно включают игроков клана, которые могли участвовать в рейде, но не совершили атак.
`RaidRepo` объединяет эти данные и формирует показатели количества активных и подходящих участников, полностью
использовавших атаки, а также участников без атак. Долевые метрики рассчитываются относительно состава конкретного
рейда, поэтому сравнение корректно работает при изменении количества участников.

# Telegram

## telegram_chats

Хранит зарегистрированные Telegram-назначения.

Назначение определяется парой `(chat_id, message_thread_id)`:

* `chat_id` — ID Telegram-чата или группы;
* `message_thread_id` — ID темы форумной группы;
* `message_thread_id = 0` — общий чат без отдельной темы;
* `title` — локальное описание назначения.

Каждая запись представляет отдельного получателя уведомлений. Несколько записей могут иметь один `chat_id`, если
уведомления должны отправляться в разные темы одной форумной группы.

---

## clan_subscriptions

Связывает кланы и Telegram-назначения.

В таблице хранятся `clan_tag`, `chat_id`, `message_thread_id` и `audience`. Поле `audience` определяет, какие
уведомления получает назначение:

* `players` — отчёты и напоминания для участников клана;
* `management` — отчёты о нарушениях, надёжности состава и системные сообщения для руководства.

Первичный ключ состоит из:

* `clan_tag`;
* `chat_id`;
* `message_thread_id`;
* `audience`.

Используется связь "многие ко многим":

* один клан может иметь несколько подписчиков;
* один Telegram-чат может быть подписан сразу на несколько кланов;
* разные темы одного Telegram-чата могут быть подписаны независимо.
* одно и то же Telegram-назначение может иметь отдельные подписки для обеих аудиторий.

Во время обработки событий `NotificationService` получает список назначений из этой таблицы с фильтрацией по аудитории.
Миграция `007_subscription_audience.sql` добавляет поле `audience` и переносит существующие подписки в аудиторию
`players`.

# Уведомления

## notifications

Хранит информацию об уже отправленных уведомлениях.

Первичный ключ:

* event_type
* event_id
* chat_id
* message_thread_id

Благодаря составному первичному ключу одно и то же событие может быть независимо доставлено в несколько чатов или
тем одного и того же чата.

Это обеспечивает идемпотентность системы уведомлений и исключает повторную отправку одного события одному и тому же
назначению.

Аудитория не входит в первичный ключ `notifications`: разные аудитории используют разные `event_type` для одного
доменного события, например `war_ended` и `war_violations`, а для рейдов — `raids_ended`, `raids_comparison` и
`raids_violations`. Поэтому обычный, сравнительный и управленческий отчеты дедуплицируются независимо.

Для временных уведомлений о войне или рейдах `event_id` содержит идентификатор события и тип контрольной точки,
например:

```text
42:started
42:six_hours_left
42:one_hour_left
15:twenty_four_hours_left
15:one_hour_left
```

Отдельная таблица для временных напоминаний не требуется: они используют ту же таблицу `notifications`, что и отчёты о
завершённых событиях.

Миграция `006_telegram_topics.sql` переносит существующие записи на `message_thread_id = 0`, то есть сохраняет их как
назначения общего чата.

# Индексация

Для наиболее часто используемых запросов созданы специализированные индексы.

Основные задачи индексации:

* быстрый поиск активных участников клана;
* получение последних снимков игроков и кланов;
* выборка истории конкретного игрока;
* построение отчетов по войнам;
* получение данных по сезонам CWL;
* анализ рейдов;
* ускорение поиска подписчиков клана.

---

# Архитектурные принципы хранения данных

База данных построена с учетом долгосрочного хранения истории.

Основные принципы:

* текущее состояние отделено от исторических данных;
* аналитика строится на основе снимков состояния (snapshots);
* история членства игроков сохраняется полностью;
* большинство сущностей привязано к конкретному клану через `clan_tag`;
* система поддерживает одновременную работу с несколькими кланами;
* уведомления являются идемпотентными благодаря журналу отправленных событий;
* внешние ключи и каскадное удаление обеспечивают целостность данных.
